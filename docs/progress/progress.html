OpenTSense · Final year project · status at 11 Nov 2026

Seven stages from a real CPU to a hidden die's temperature

An open testbed that takes a real routed chip, runs real programs on it, turns the switching into power and heat across a 3D stack, and asks how well a few sensors can recover a die buried inside. Six stages are built and checked; estimation is the next phase.

The pipeline

1 Cells→2 Activity→3 Power maps→4 Stack→5 Temperature→6 Leakage loop→7 Estimation

Every stage was built twice. An exploratory pass (gates G30 to G69, before 1 November) showed the idea works. The project pass (G70 onwards) rebuilt it in one repository with pinned tools, and each stage counts as done only after it passed a gate: a test whose pass bar is written down before the run.

How each stage was developed

1

Cells: physical design

Done
What
Turns the chip's source code into a real layout: every logic cell gets a position on the silicon.
Tools
OpenROAD flow (Yosys synthesis, placement, routing); ASAP7 7 nm, IHP SG13G2 and SKY130 open process kits.
Developed
The ibex RISC-V CPU routed on three kits, plus a TPU accelerator and the larger cva6 core (G52: zero layout errors). In the project pass the tool image is pinned by digest, so layouts rebuild identically. G70 passed: clean builds in about 3.5 minutes, end-to-end smoke test.
Result
About 70,000 placed cells on ASAP7 ibex, with locations exported for the power maps.
2

Activity: which wires switch, and when

Done
What
Runs real programs on the gate-level chip and records every wire flip, because switching is what costs power.
Tools
RISC-V compiler, Embench-IoT benchmarks, testbenches, Icarus Verilog (accurate) and Verilator (fast).
Developed
G72 passed with 4 kernels on ibex and 3 TPU workloads, all answers correct. Then G81a failed: Verilator's power disagreed with Icarus. The cause was the testbench feeding unknown (X) values on a memory bus, which the two simulators treat differently. After a one-line fix, G81x passed: within 0.45 %, 37 times faster. G81b passed with whole Embench programs (19 plus an idle program), and G81d2 passed with a real CPU plus accelerator system (Rocket + Gemmini).
Result
Whole-program switching, plus a per-region activity timeline that tracks power at correlation 0.977 to 1.000.
3

Power maps: switching into heat sources

Done
What
Turns wire flips into watts per cell, then sums them into a grid of tiles per die.
Tools
OpenSTA (power per cell from switching, cell energy data and wire loads); the project's tiling code.
Developed
G72 passed (32 × 32 tile maps, every pin annotated). G75 passed: OpenSTA's default activity guess overstates power by 1.7 to 2.2 times compared with real programs, which is a concrete reason synthetic power maps mislead.
Result
Real-activity power maps for the CPU and accelerator dies.
4

Stack: the 3D package

Done
What
Describes the stack (dies, bonds, materials, heat sink) once, in a form every solver can read.
Developed
Exploratory stacks were hand-written per solver, which caused errors. Now one YAML file is converted automatically for each solver (G71). G93a added side-by-side chiplets (2.5D), thin sublayers and a heat sink on either side.
Result
Three stacks: single die, two dies stacked, 2.5D chiplets.
5

Temperature: three solvers, one answer

Done
What
Computes each die's temperature from its power map.
Tools
3D-ICE, PACT and HotSpot: three independent thermal simulators.
Developed
G71 passed (3D-ICE and PACT agree). G93a passed with HotSpot as a third solver. Its first run stopped on HotSpot's input-line limit, which was raised and recorded as an amendment. The temperature response is also captured as one matrix, so later stages need no slow re-solve.
Result
All three solvers agree within 0.41 K, so the reference temperature does not rest on one tool.
6

Leakage loop: heat feeding heat

Loop doneLibrary check running
What
Hot chips leak more current, which heats them more. This stage models that feedback and predicts when it runs away.
Tools
ngspice with transistor models, to measure each cell's leakage from 25 to 125 °C.
Developed
G74 passed: one number, ρ, predicts runaway (96 of 96 cases right). G75 found that the open kits' shipped libraries understate hot leakage by 2 to 16 times. Building correct temperature-aware libraries took five gates: G92 to G92d each failed on a handful of the roughly 8,500 cell states, and each failure exposed a real bug (unsettled flip-flop states, a bad reference, cells silently falling back to shipped values).
Result
The loop is done. The final library check (G92e) is running; its first kit finished with zero failed states.
7

Estimation: seeing the hidden die

Partly done
What
From a few sensor readings, recover a buried die's power and temperature.
Developed
Exploratory studies covered Bayesian recovery, Kalman filters, sensor placement and error margins. G73 passed: "degrees of freedom" predicts each die's error (correlation −0.93), and a die is hidden by its low power, not by being buried. G84 passed: one command scores any estimator and gives identical numbers on any machine. Code for a regularised-inversion estimator (G77) is written and tested.
Next
Move the exploratory estimators into the testbed and gate them (G76 to G80).

What the gates caught

Almost every stage hit a failure that the gate process caught, and each one exposed a real flaw: the unknown-value testbench bug (G81a), unsettled SPICE states (G92 series), HotSpot's input limit (G93a). That is the evidence that the testbed is checked, not only built.

How close is this to consumer 3D stacks?

Representative, not a replica. The densities and temperatures sit in consumer ranges; the dies are smaller and the CPU is an embedded core. Consumer figures below are approximate public numbers.

Fixing

Three gaps closed in the project

  • Memory: DRAMPower turns the program's real memory requests into a memory-die power map (G81e).
  • Leakage: temperature-aware libraries (G92e, running), with fast-leaking cells as the stress case.
  • Die size: consumer-sized HBM-style and three-tier stacks (G93).
Extension

Modelled power management

  • Power scaled with frequency and voltage squared, idle blocks switched off, and a simple governor choosing the operating point.
  • A model, not real firmware. Planned for the extension window in March.
Stated limits

Two gaps reported, not fixed

  • Consumer software (an operating system, games) cannot run in gate-level simulation on this hardware.
  • Real foundry process data is under NDA, so ASAP7, a predictive 7 nm kit, stands in for it.

What is new about the switching

Computing power from real switching is standard in industry. What is new is bringing it, open and reproducible, into 3D thermal-sensing research, which still relies on synthetic power maps. The project also measures how much that shortcut distorts the results (1.7 to 2.2 times), and finds that a chip's own activity timeline tracks power almost exactly, so activity counters could act as extra sensors for a hidden die.

Where the tools run

Everything runs on one Windows laptop. The chip and thermal tools are Linux programs, so they run in pinned Docker containers, which Docker Desktop hosts inside WSL 2. The analysis code runs on Windows directly.
